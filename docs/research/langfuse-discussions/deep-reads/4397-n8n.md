# #4397 — "n8n Integration"

- URL: https://github.com/orgs/langfuse/discussions/4397
- Category: Ideas · Votes (2026-07-10): **381** (task estimate ~371; actual higher)
- Comments: **46** — by far the #1 demand item in the entire corpus.

## What people ask for

Native tracing of **n8n workflows** — not just LLM calls, but a **span per node**
across the whole workflow (including sub-workflows). The top request is
observability parity with how n8n users already use Flowise/Langflow. Volume of
"Bump" comments (dozens) shows sustained, unmet demand over ~18 months.

## Maintainer answers (@marcklingen, MEMBER)

- "n8n seems to be based on LangChain, so the existing **LangChain integration**
  could be reused (similar to Langflow and Flowise)." (up=10)
- **The blocker is on n8n's side:** "As n8n is a platform product, we cannot build
  an external integration as this needs to be added to the n8n project itself…
  this very much depends on open tracing/instrumentation capabilities in n8n
  which do not exist." (up=5)
- Interim workaround endorsed by maintainers and users: **proxy n8n's LLM calls
  through LiteLLM** → Langfuse. Works for LLM logs only, **no detailed agent/node
  traces** (@simple10 up=5, marcklingen).
- Partial ship (2025-07-06): a **Langfuse n8n community node for prompt
  management** (not tracing). up=8 rx=13. "No update on tracing integration."
- Community effort: `rorubyy/n8n-nodes-openai-langfuse` traces OpenAI-compatible
  calls; another user (@biliboss) built a workflow that pulls n8n execution IDs
  via REST and maps them to the Langfuse API.

## What n8n actually emits

- Nothing OTLP-native today. n8n has **no built-in OpenTelemetry/tracing hooks**
  — the whole thread's blocker. Available signals:
  1. **LLM calls** if routed through a LiteLLM/OpenAI-compatible proxy (LLM
     spans only, no workflow structure).
  2. **Execution data via n8n's REST API** (`/executions/{id}`) — node inputs,
     outputs, and sub-workflow structure, pullable **post-hoc** (@biliboss).
  3. Community OTel instrumentation experiments exist
     (community.n8n.io/t/n8n-successfully-instrumented-with-opentelemetry).

## As an LLMObs plugin / normalizer

This is a **community/first-party compat plugin (cold path), not a hot-path
normalizer** — n8n does not emit OTLP, so there is no wire dialect to normalize.
The right shape:

- A **compat-ingest plugin** with its own endpoint that either (a) accepts n8n
  webhook/execution-finished payloads or (b) polls the n8n REST API for execution
  data, then **maps n8n's node graph → canonical spans** (workflow = trace, each
  node = span, sub-workflows = nested spans) and writes via the SDK `write`
  primitive. Raw n8n attributes preserved alongside canonical fields.
- If/when n8n ships native OTLP export, this collapses to a thin normalizer in
  `kernel/internal/dataplane/normalize/` and the compat plugin becomes optional.

**Strategic read:** Langfuse *structurally cannot* build this ("must be in n8n
core"). LLMObs's compat-plugin model means a **community author can ship n8n
tracing as a container + manifest without touching kernel code** — this is the
single highest-demand item in the corpus (381 votes) and the flagship proof of
the plugin thesis. It belongs at the top of the plugin roadmap.
